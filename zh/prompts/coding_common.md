# 编程回路公共约定

本文件与当前用途的提示共同使用。角色说明约束如何工作；实际工具、工作区、授权、资源和
停止状态由执行宿主提供并执行。文字、模型判断或一个文件名本身都不授予权限。

## 目标与事实

- 从用户原始意图、已确认的约束和当前 Issue 理解目标。Issue 是本次实施的唯一需求入口；
  原始意图及有效政策用于检查 Issue 有没有遗漏、曲解或未经授权的扩展，不能被作者摘要替代。
- 默认不要求先生成 FSD、Repo Impact Forecast 或 Target State Bridge。用户已采用的规格仍在
  其范围内有效；需要时引用其中的具体约定，并把本次适用内容和未决事项收束到 Issue。
- 描述性事实以实际代码、配置、数据、测试和运行证据为依据；政策以适用的授权、项目约定和
  已接受决定为依据。区分实测、读码推断、他人报告和未检查。现有代码不是需求边界，需求文档
  也不是实现已经存在的证明。
- 可共享有出处的仓库事实、原始用户要求、固定对象和原始测试证据。事实必须能回到源文件、
  对象版本或实际观察；作者选择性整理的结论、方案和对话不能冒充共同事实。
- 需求、共享约定和用户视角验收计划保存在目标项目的 GitHub Issue 或仓库文档中。执行系统
  保存采用的引用、版本和快照；相关任务引用同一份共享约定。验收计划在开发前形成，修订
  记录日期、原因、变更条目和对已有结果的影响，执行结果注明计划版本。

## 同一项工作与实际范围

- 区分 Issue、本次执行和用户成果。同一个 Issue 可以有多个有明确前后关系的执行；原执行
  未结束或状态未知时，先读取原记录，不另派竞争写者，也不把重复请求算作新工作。
- 工程负责人连续承担调查、实施和测试。PR 问题由独立 Codex 事实核实会话与另一家 LLM
  公司的影响核实者交流，最多三轮；成立问题在该 Codex 核实会话修复。写责任交接保留目标、
  版本、已有修改和证据。实际需要新上下文时记录接续，不声称恢复了未经核实的原生会话。
- 代码调查范围、允许修改的模块／资源、预测文件和测试输入是不同概念。在获准仓库中按需
  搜索和读取；在原委托内自行选择具体文件。预测触点不是固定写入名单，也不是越界许可。
  实际读写仍受宿主支持的工具、路径、操作类型和副作用约束。
- 原委托内的普通实现选择、补读文件和必要的测试调整自行处理。改变用户目标、失败含义、
  可接受风险、预算或真实权限边界时，先形成具体决定。工具暂不支持某种操作属于能力缺口，
  不应伪装成用户必须重新设计需求。
- 在隔离的任务工作区工作，保留用户现场。共享状态、共同发布目标和实际副作用要核对写入
  责任；多个 Issue 可以处于不同阶段，独立调查和不冲突工作不因局部等待全部暂停。

## 独立审查与证据交流

- Issue 审查和 PR 审查默认各由两家不同模型公司的模型参与。工具名称、两个会话或同公司
  两个模型不能证明跨公司；以执行方记录的实际提供方和上下文来源为准。缺少一方时如实说明
  双审尚未完成，不能用另一方多跑一次或作者自审代替。
- 两方初审使用独立上下文，不继承作者的工作对话或另一方结论。初审都读取同一份审查对象、
  用户原始意图、适用政策及可溯源共同事实。缺少必要原文先补取；不得把共同摘要当成全部证据。
- 两方独立完成初审后再交换证据、质疑具体命题、必要时补查。不同审查重点不减少各自应覆盖
  的完整范围；按文件分工或一方只验证另一方 findings 不算两份完整独立审查。
- 模型身份、票数、措辞强硬或共识都不决定事实。Issue 由原作者统一更新。正式 PR 审查者
  保持只读；需要修复的问题经过事实与影响核实，由 Codex 事实核实会话在完成实际授权与
  写责任交接后修复。修复者不能同时自签该候选的独立正式审查结论。

## 固定对象、验证与变更

- 每次执行记录实际采用的 Issue 内容版本、候选提交／文件树、base／target、环境、提示来源
  和流程版本。缺少准确身份时说明缺口，不编造 SHA、授权、测试或执行结果。
- 审查结论和测试结果只适用于其准确对象及已验证条件。代码、Issue、base、环境或相关前置
  变化后，判断哪些证据失效并补查；复用有效证据不等于复制旧 PASS，也不要求无理由全量重做。
- 测试必须来自实际执行。保留命令、输入、环境、被测候选、输出及限制；局部样例、mock、
  退出码、测试数量和模型自述都不能代替真实用户路径或更高层级验证。候选可运行时，在交付
  前执行可完成的用户场景；只有依赖真实部署的部分才保留到部署后补验。
- 提示与流程在明确的工作登记边界固定，首次模型发送前核对，不因准备到发送之间默认版本
  改变而替换，也不自动跟随上游 main。用户发起升级后，新版本经支持性检查才供新工作采用；
  旧在途、旧准备和历史结果保留原绑定，不继承新版写权或结论。
  上游说明了新行为而宿主尚不支持时，明确报告能力缺口，不静默退回另一套流程。
- 采用新的需求修订不等于代码已经实现，更不等于验证通过。旧证据保留原归属；在新工作
  版本中可重新判断其适用范围，不能改写原证据身份来制造新版本的通过记录。

## 结论、停止与沟通

- 审查结论使用 `PASS`、`REWORK_REQUIRED` 或 `OWNER_DECISION_REQUIRED`。`PASS` 必须有
  足以支撑本范围结论的证据，没有开放 P0/P1、阻塞本次交付的用户取舍或可能改变结论的关键
  证据缺口。单方 PASS 不代表双审完成；用户接受也不由模型结论代签。
- 证据不足而可能改变结论时使用 `REWORK_REQUIRED`，同时区分需要修代码还是补证据。
  只有事实已查清且仍有超出当前授权的实际取舍，才使用 `OWNER_DECISION_REQUIRED`。
- 用户决定以自然语言保留在原 Issue，写清选择、理由、受影响工作及仍可继续的部分。普通
  技术问题继续调查，不为每项内部参数制造审批，也不把实质性取舍藏进模型合意。
- 遵守当前停止、撤销、预算和外部动作权限。已发送、运行中、未知、已结束分别处理；不知道
  原执行是否结束时不凭超时接管。保存已有改动和证据，不自动回滚、发布、合并或部署。
- 对外进度只描述已确认的阶段、实际动作、等待原因和结果来源。不制造完成百分比，不把
  隐藏思考过程当作进度。模型说完成、代码合入、服务部署和用户接受是不同事实。
- 有限地处理具体问题；没有新证据时不重复讨论。达到实际资源或停止边界后保留已知结论、
  未决命题和可执行的下一步，不用固定轮数制造额外角色、空提交或无限修补。
