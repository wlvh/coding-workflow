# 编程公共约定

与当前任务的角色提示一起使用。

## 目标与调查

- 读取用户原始要求、当前 Issue、已确认决定和项目 AGENTS.md，明确目标、适用约定与完成标准。
  共享规格直接引用其相关部分；新增目标和重要取舍记回 Issue。
- 用源码、配置、测试和实际运行核对事实，用有效项目约定核对政策。说明结论来自实测、
  读码推断还是他人报告；影响判断的原始材料缺失时先补取。
- 根据真实调用链和用户路径调查已有能力、依赖及影响。优先复用已有实现，选择满足目标的
  最小充分改动；文件范围随调查更新。

## 实现与接续

- 同一工程负责人连续调查、实施、测试和处理审查反馈。更换会话时交接当前版本、实际改动、
  已验证结果、未决问题和下一步。
- 按项目授权使用工作区和工具，保留用户已有修改。普通实现选择自行处理；需要改变目标、
  公共行为、可接受风险或资源范围时，提出具体选择及影响。
- 并行工作先明确修改范围和共享状态的负责人。中断后核实原操作与工作区状态再继续；
  收到停止要求时停止后续操作，保留已有改动和验证记录。

## 独立审查与交流

- Issue 和 PR 均由来自两家不同 LLM 公司的 LLM 审查。两方先在独立上下文中读取同一版本的
  审查对象、原始需求和可追溯事实，各自完成完整初审，再交换结论与证据。
- 初审使用项目材料，保持与作者工作对话及另一方结论隔离。每方检查完整范围，明确自己的
  发现、依据与未检查项；双方均无阻断问题时，也简短交流并确认对象和覆盖范围。
- Issue 由原作者统一修改，代码由原工程负责人修复。审查者复核修改和反证，对新版本分别
  给出结论。事实争议用代码、测试或复现解决；产品取舍交用户决定。

## 验证与结论

- Issue 阶段明确验收场景。开发中使用实际候选、所需配置和依赖执行项目验证；候选可运行时
  尽早走真实用户入口，部署后补验目标环境特有行为。
- 保存实际命令、受测版本、相关环境、输出和未覆盖范围。候选、验证定义和必要环境相同且
  结果仍有效时复用证据；后续失败或未知执行先核清，变化后补验受影响部分。
- 审查结论使用 `PASS`、`REWORK_REQUIRED` 或 `OWNER_DECISION_REQUIRED`。范围内无开放 P0/P1、
  阻断性产品取舍和关键证据缺口，且完整覆盖有证据支持时给出 `PASS`；需要修复或补证据时
  给出 `REWORK_REQUIRED`；事实已清楚但仍需用户取舍时给出 `OWNER_DECISION_REQUIRED`。
- 说明当前结果适用的版本、已完成的验证及剩余工作。原目标的实现缺口继续修复，新增期望
  回到 Issue 确定。讨论没有新证据或达到资源边界时，保留未决问题和可执行的下一步。
