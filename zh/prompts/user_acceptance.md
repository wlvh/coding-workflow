# 用户视角验收计划与执行

## 开发前：记录用户怎样验收成果

读取用户原始意图、已确认边界和当前 Issue。围绕用户会实际进行的操作形成简洁验收场景：
谁从什么入口开始，需要什么真实或代表性输入，关键操作与预期结果是什么，重要失败后如何
识别和继续。预期结果必须来自用户目标或有效政策，不能从当前实现反推“只要这样就算成功”。

将场景、必要前置和可判定标准写入目标项目 GitHub Issue 的验收章节，或 Issue 引用的仓库
验收文档，由原 Issue 作者统一维护，记录初版。能在本地或候选环境检查的部分，与确实依赖
部署环境的部分区分。现有场景能复用就引用和扩展。

由 Issue 双审的两家不同 LLM 公司的 LLM 检查计划的完整性与最小充分性。
目标行为有分支或状态时，沿同一 Issue 的流程说明（必要时图示）手动推演；有歧义回到原目标补齐。

## 开发中：允许修订，保留文档记录

调查或实现发现需要调整步骤、输入、账号、环境或场景时，工程负责人提出有证据的修订，
由原 Issue 作者沿同一维护路径更新 GitHub 上的计划正文。记录修订日期、原因、修改前后
条目、采用依据和对已有验收结果的影响。保留原计划及修订历史。

原目标内的执行细化可沿既有委托处理；改变目标、范围或关键成功／失败判据时，先写回 Issue
决定，再由两方检查受影响的验收要求。旧结果继续对应旧计划，说明它对新版哪些条目仍适用，
哪些需要补验。

## 候选阶段：交付前实际走用户入口

固定验收计划版本、准确候选及运行环境，使用已授权的运行、浏览器、CLI 或交互工具执行适用场景。直接
观察输出、状态和用户可见副作用，保留版本、输入、步骤、原输出和必要截图／日志。
未运行的场景标为未验。

复用该候选已经存在且条件匹配的真实验证；只补它没有覆盖的用户层行为。测试所见的代码、
配置、依赖、数据与实际用户入口有差异时写清限制及未覆盖的路径。
必要权限、环境或输入缺失时，说明具体未验项和补验条件。

发现现有目标未满足，记录复现输入、操作、实际与预期结果，交入问题核实流程；需要修复时
由 Codex 事实核实会话修复，再对新候选复审和验收。新增期望由用户决定是否纳入对应工作
版本。

## 部署阶段：只补环境相关缺口

部署后核对实际部署版本和必要配置，执行那些只有此环境才能证明的场景，并检查部署差异
是否使先前证据失效。环境变化按影响补验。

## 报告与成果接受

按场景说明计划版本、已观察结果、证据、未检查部分和限制，指向同一 Issue 的完成标准。
说明判断适用于候选、实际部署还是其中明确的一部分。需要结论时使用：

- `PASS`：本次验收范围内无未解决的阻断问题，实际证据充分。
- `REWORK_REQUIRED`：需要修复实现或补充验收证据。
- `OWNER_DECISION_REQUIRED`：事实已查清，仍需用户决定超出既有委托的取舍。

记录用户实际接受的对象与未决工作。
