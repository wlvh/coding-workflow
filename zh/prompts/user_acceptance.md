# 用户视角验收计划与执行

与 [编程回路公共约定](coding_common.md) 一起使用。本提示用于同一 Issue 的早期验收设计、
可运行候选验收和必要的部署补验；三者是执行时点，不要求新增三名 agent 或三份独立规格。

## 开发前：记录用户怎样验收成果

读取用户原始意图、已确认边界和当前 Issue。围绕用户会实际进行的操作形成简洁验收场景：
谁从什么入口开始，需要什么真实或代表性输入，关键操作与预期结果是什么，重要失败后如何
识别和继续。预期结果必须来自用户目标或有效政策，不能从当前实现反推“只要这样就算成功”。

将场景、必要前置和可判定标准写入目标项目 GitHub Issue 的验收章节，或 Issue 引用的仓库
验收文档，由原 Issue 作者统一维护，记录初版。能在本地或候选环境检查的部分，与确实依赖
部署环境的部分区分；不用“将来上线再看”推迟已经能做的验证。
现有场景能复用就引用和扩展，不为每条需求额外创建一份验收平台或穷尽全部未来输入。

两公司 Issue 审查检查这份计划的完整性与最小充分性，不再固定增加一对验收计划审查模型。
目标行为有分支或状态时，沿同一 Issue 的流程说明（必要时图示）手动推演；有歧义回到原目标补齐，不新建
并行的批准文档。

## 开发中：允许修订，保留文档记录

调查或实现发现需要调整步骤、输入、账号、环境或场景时，更新同一份计划，并记录修订日期、
原因、修改前后条目、采用依据和对已有验收结果的影响。保留原计划及修订历史，不能只在聊天
中口头换标准，也不能为了让当前实现通过而删除失败场景或放宽原目标。

原目标内的执行细化可沿既有委托处理；改变目标、范围或关键成功／失败判据时，先写回 Issue
决定，再由两方检查受影响的验收要求。旧结果继续对应旧计划，说明它对新版哪些条目仍适用，
哪些需要补验。计划正文保存在 GitHub，执行系统记录本轮采用的版本和快照。

## 候选阶段：交付前实际走用户入口

固定验收计划版本、准确候选及运行环境，使用已授权的运行、浏览器、CLI 或交互工具执行适用场景。直接
观察输出、状态和用户可见副作用，保留版本、输入、步骤、原输出和必要截图／日志。代码
阅读、截图设计稿、mock、作者报告或仅写了计划，都不能写成场景已实测。

复用该候选已经存在且条件匹配的真实验证；只补它没有覆盖的用户层行为。测试所见的代码、
配置、依赖、数据与实际用户入口有差异时写清限制，不能把低层测试通过升级为端到端通过。
必要权限、环境或输入缺失时，说明具体未验项和补验条件，不伪造通过，也不擅自使用外部
账号、生产数据或增加实际副作用。

发现现有目标未满足，记录复现输入、操作、实际与预期结果，交入问题核实流程；需要修复时
由 Codex 事实核实会话修复，再对新候选复审和验收。新增期望由用户决定是否纳入对应工作
版本；不能不断改变预期来使当前实现通过。

## 部署阶段：只补环境相关缺口

部署后核对实际部署版本和必要配置，执行那些只有此环境才能证明的场景，并检查部署差异
是否使先前证据失效。环境变化按影响补验，不机械重做全部有效测试，也不把候选通过直接
复制为部署通过。

## 报告与成果接受

按场景说明计划版本、已观察结果、证据、未检查部分和限制，指向同一 Issue 的完成标准。需要 verdict
时使用公共出口：关键失败或可能改变结论的缺口不能 PASS。报告说明当前判断适用于候选、
实际部署还是其中明确的一部分，不能把待部署补验藏在“全部完成”中。

模型可以提出接受建议，用户成果接受由有效的用户决定或其明确委托确定。记录实际接受
对象与未决工作；不要以模型报告、PR 合并数或自动关闭按钮替用户宣告目标已经完成。
