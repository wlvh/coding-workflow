# 开发后的 Tech Lead 解读：成果、机制与取舍

与 [编程回路公共约定](coding_common.md) 一起使用。在开发、修复和必要验证完成后，站在
技术负责人视角，基于实际源码、准确候选和开发／审查／验收记录，帮助项目负责人理解成果、判断取舍，
并提出下一步准确要求。解释按可感知成果组织，可覆盖一项 Issue 的多个 PR；不要求每个
PR 重复生成一份完整长文，也不把解释报告变成新的审查或授权关卡。

## 先讲用户获得什么

清楚说明改动前如何工作、本次解决什么问题、用户现在如何使用、已交付到哪个环境，以及
哪些仍是候选能力、待部署验证或未完成工作。用具体输入、操作和结果建立理解，区分新增、
改变和退出的能力。不要把“增加若干校验／工具／文件”当成用户价值。

## 再讲实际机制和取舍

围绕关键机制连接入口、数据变化、模块职责、状态、权限、读写和输出，解释正常路径与
现实可达的失败／恢复路径。让读者能够手动推演：什么条件下做什么、失败后留下什么、
如何继续、为什么这次改动能改变结果。仓库术语先用大白话解释；源码与函数名用于核对，
不能成为理解正文的前提。

流程图、时序图或具体例子应成为关键机制的说明，不是装饰。图与正文对应实际实现；
预期行为、已经实现但未运行和本轮实测分开。需要精确规则时用已经解释过的业务对象写
伪代码，不把源码删短或逐行翻译后当作解释。

## 解释开发过程中怎样作出选择

从 Issue、PR、代码变化和开发记录中选出真正影响结果的决定：最初考虑了哪些方案，调查、
测试或审查带来了什么新证据，最终为何选择当前方案。说明曾经删掉、复用、延期或保留的
内容，解决了什么问题，又付出了什么代价；不要把事后想到的理由写成当时做过的判断。

回看本次开发，如果减少约 50% 开发量，最小方案是什么，保留和放弃哪些用户价值？基于
实际机制说明可删部分与必要部分；没有足够证据时标明假设。说明用户视角验收计划采用了
哪一版、开发中为什么修改、结果如何，以及哪些取舍已经得到验证。

保留影响判断的边界，其他细节按需展开；不抄函数目录、堆能力清单或用“更加可靠”替代因果。
跨仓库依赖和真实消费者确实影响成果时，解释它们怎样参与和哪里仍未验证。

## 证据、指引与下一步

重要结论链接准确版本的代码、Issue、PR、测试或运行证据，区分设计意图、实现事实和推断。
流程图节点引用源码时使用 GitHub 固定版本文件，不靠行号替代解释。复用已有解释时标明
适用版本，补充本次变化，不把旧报告直接当作新成果证据。

核对用户能否通过 AGENTS.md 的任务路由、正式使用文档和实际入口利用成果；缺少或失真的
指引交回原工程负责人更新。说明完成标准的实际达成情况、已接受的取舍、剩余验证和真正
有价值的下一步。没有明确收益的改动不要推荐。

采用用户要求的交付形式。需要离线 HTML 时，完整叙述和关键图表须离线可读；交互或悬停
只能补充细节，不依赖它们才能读懂主线。是否存档、发布评论或发送他人，遵循当前授权。
解释不替代双公司审查、真实用户路径验收、合并授权或用户成果接受。
