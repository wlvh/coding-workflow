# 编程工作流

## 1. 编写 Issue

调查相关代码和已有功能，将需求写成一份可实施的 Issue：

- 用户要解决的问题，以及完成后的行为。
- 本次范围、必要的接口与兼容要求。
- 验收的初始条件、操作、预期结果和关键失败行为。

需要共享约定、数据迁移或分阶段发布时，在 Issue 或关联文档中补充。只有确有不同负责人并行推进、
且可独立实施和验收的工作，才拆成子 Issue。

使用[Issue 写作提示](../../prompts/issue_agent.md)。

## 2. 审查 Issue

由**来自两家不同 LLM 公司的 LLM**，在独立上下文中审查同一版 Issue、原始需求和相关代码事实：

- [完整性与可验收性](../../prompts/issue_review_completion.md)：是否忠实于用户目标，必要行为是否齐全，验收能否判断成功与失败。
- [最小充分性](../../prompts/issue_review_minimality.md)：哪些要求可以删除、合并或复用已有能力，怎样用更少的改动完成目标。

两方先独立审查，再交流发现。Issue 作者统一修改正文，两方复核修改和未解决问题。
阻断问题解决后进入实施；审查中新提出的功能想法单列，由用户决定是否采用。

## 3. 实现、测试并提交 PR

同一工程负责人（编程 agent）连续承担调查、实现、测试和后续修复。按项目约定阅读相关源码、调用方与测试，
选择最小充分的实现方案；随着调查深入调整修改范围。涉及目标、公共接口或兼容约定的取舍，写回 Issue。

优先复用已有代码和测试，补充能覆盖新增行为、关键失败路径及模块组合的验证。
代码可运行时就执行 Issue 中的用户场景。候选内容、验证定义和必要环境相同时，可复用有效测试结果；
出现后续失败时，先查明原因再采用结论。

完成自审，更新受影响的使用说明和项目文档，创建或更新 Draft PR。正文说明实际变化、测试结果和未解决问题，
并关联 Issue。更换会话时，交接当前代码、已验证结果、未决问题和下一步。

使用[工程负责人提示](../../prompts/engineering_owner.md)。

## 4. 审核 PR，处理反馈

由**来自两家不同 LLM 公司的 LLM**，在独立上下文中分别完整审查同一代码版本。
两方使用[完整 PR 审核规范](../../prompts/pr_review_system.md)，分别加强
[正确性](../../prompts/pr_review_correctness.md)与[影响及必要性](../../prompts/pr_review_impact.md)检查。

两方先独立阅读代码和测试，再按[证据交流提示](../../prompts/review_exchange.md)交换发现与结论。
即使初审均无阻断问题，也要简短交流，确认代码版本、覆盖范围和有无遗漏。

每个问题给出触发条件、代码依据和实际影响。原工程负责人修复或提供反证，两方复核改动及相关影响，
对更新后的代码版本给出结论。技术争议用源码、测试或复现解决；产品取舍交用户决定。
两方均确认通过后进入集成。

## 5. 集成与发布

将改动与目标分支及相关成果组合，验证接口、配置、依赖和完整使用路径，复用仍适用的测试与审核结论。

集成修改代码、配置、依赖、启用方式或连接关系，实质影响已审行为或原证据适用性时，补充测试，
并由两方审查 LLM 对新版本的差异及影响给出结论。复审聚焦受影响部分。

按[集成接收提示](../../prompts/integration_acceptance.md)核对最终版本、审核结论和验证结果，
由审查 LLM 确认交付条件，再按项目流程合并和发布。

## 6. 验收用户成果

按 Issue 中的场景，从实际使用入口检查成果。验收在可运行的候选上尽早进行，
部署后补充目标环境特有的验证；跨多个 PR 的成果统一验收。

原目标的实现缺口交回工程负责人修复；目标、范围或关键行为发生变化时，先更新 Issue。
交付说明写清成果在哪里、怎样使用、验证了什么以及仍有哪些限制。
复杂机制可用示例或流程图解释。

使用[用户验收提示](../../prompts/user_acceptance.md)和[交付说明提示](../../prompts/delivery_explanation.md)。
