# 编程工作流

本规范定义从用户需求到可交付软件成果的编程回路，供人和 Tongxu 等执行系统采用。
当前为 **coding-loop v2**；决策依据见 [DEC-009](decisions.md#dec-009issue-直接驱动的编程回路与固定版本采用)。
[角色提示与源索引](../../prompts/README.md)是模型行为指令的唯一维护入口；
[固定版本采用与更新](version_adoption.md)定义下游怎样采用本规范。

本仓库发布规范与提示，不以文档更新宣称 Tongxu 已具备相应运行能力。
执行系统固定采用一个准确提交，验证配套控制流程后再对新工作启用；不在运行时追随 main。
非编程秘书、项目管理、账号与执行器实现仍归相应产品。本次规则不改变下文独立的 Workflow Docs Sync Skill。

## 目标与默认安排

默认工作线是：形成 Issue、跨公司需求双审、同一工程责任调查实施与测试、跨公司 PR 双审、
准确候选的集成接收与按委托交付、完整用户成果验收。调查、实施和测试交替进行；
新需求协调、进度展示、停止与恢复贯穿全程，不为每一项能力固定增加一个模型或文档。

- FSD Core Contract、Repo Impact Forecast、Target State Bridge 退出默认前置产物链。
  共享行为约定、决定性影响结论、迁移或分阶段发布安排按真实需要保留在 Issue 或被引用的共享文档中。
- 同一工程负责人连续调查、实施、处理反馈；会话可以更换，准确工作依据与原责任必须延续。
- Issue 和 PR 均由两个不同公司的模型独立审查并交流。不同角色、prompt、会话或同公司的不同模型
  不等于跨公司。供应商组合可配置；缺少第二家时如实显示审查未完成，不静默降级。
- 既有委托充分时自主继续。普通实现选择不增加固定计划批准；产品目标、关键语义或权限确需改变时
  处理对应决定。提示、模型共识和通过结论都不产生写入、合并、部署或费用权限。
- 用已有记录复用事实和有效证据，保留失败与未知。减少重复调用不能代替必要的独立调查。

## 1. 新需求进入已有项目

默认项目中有多项处于不同阶段的 Issue。新需求先保存，再由项目协调入口定位相关目标、Issue、
工程责任、候选和共享约定；处理重复、补充、依赖、语义冲突、资源冲突及发布顺序，不机械新建 Issue。
秘书可以定位和推动协作，真实技术兼容性由工程责任调查，产品取舍由有效委托所确定的决定者处理。

疑似关联不是已确认冲突。只调整受影响的任务或阶段，无关工作继续；同一共享资源的写入仍需协调。
只有真正需要等待生产者输出的阶段才等待，并核对实际消费的输出版本。多任务存在不等于无限并发写入。
跨已有范围协作必须保留原来源和授权，不能通过合并列表扩大范围。

收件与启动处理分开，忙碌时仍可保存补充。已收到、已关联、已送达、已处理、已纳入工作版本、
候选声称实现和验证通过分别由实际记录支持；不得把送达显示为已实现。

## 2. Issue 直接表达目标，并给出初版验收安排

使用源索引中的 `issue_author`。Issue 是开发需求入口，引用用户原话、有效决定和必要共享约定。
内容随任务复杂度取舍，至少能回答用户问题、目标行为、必要边界和怎样判定完成；
有真实依赖、兼容要求或未决产品取舍时再展开，不填写无用章节。

验收从这里开始：明确初始条件、操作、可观察结果和必要失败语义。开发过程中补齐命令、数据、
账号或环境条件；能够提前执行的用户路径在候选阶段执行，只有目标环境能证明的部分在部署后补验。
一个成果可以跨多个 Issue/PR，共享验收场景，不为每个内部 PR 重建完整计划。

复杂功能应让用户看懂完成后的使用方式和关键系统行为，展示直接来自当前 Issue 与共享约定。
必要时作编码前解释，不强制独立 Readback、详细 HTML 或额外批准。展示不能成为第二套需求权威。

## 3. 两家公司独立审查 Issue

对同一 Issue 版本分别使用 `issue_review_completion` 和 `issue_review_minimality`：

- 完整性与可验收性：检查是否忠实于原目标、是否遗漏必要行为、成功与重要失败是否可判定。
  不因可以想象更多情况就扩大需求。
- 最小充分性：优先删除、复用、合并和缩小；检查是否为方案自己制造的问题建设新机制。
  不要求固定减少百分比，也不能删去真实必要功能。

双方先独立判断，再交换重要发现；不得继承作者工作对话或先看另一方结论再冒充独立审查。
双方都看到原始需求、同一 Issue、可追溯仓库事实和相关工作，并可补查决定性事实。
共享资料不免除必要核查，不要求各自产出完整实现方案、文件预测或测试体系。

意见分为阻断问题、非阻断建议和新增想法。新增想法未经采用不进入任务；双方同意不扩大用户需求。
原 Issue 负责人更新同一 Issue，审查者核对变更和未解决阻断项。没有独立固定综合者。
未变且仍适用的材料可以复用；不得由作者自称“小任务”跳过需要的双审。

## 4. 同一工程负责人调查并实施

使用 `engineering_owner`。开始工作固定采用的需求快照、代码起点 H0、已有委托、流程与提示版本。
先只读调查，在现有委托内继续实施；不预先穷举所有文件，不为普通实施安排设固定人类批准节点。
先按项目 AGENTS.md 与真实任务路由读取相关规范、代码、调用方和测试，不要求每次全读所有文档。

### 编码前理解方案

对于复杂或高风险 Issue，或用户希望先理解方案时，由工程负责人结合已查明的代码事实作一次解读：

```text
当前 Issue 尚未开始编码。请站在 Tech Lead 视角详细解读，目标是让我真正理解它将如何工作，而不是复述原文。
1. 目标、核心价值；
2. 落地后的具体 case：从输入、操作到结果，说明相关模块如何配合，以及关键失败情况；
3. 如果减少约 50% 开发量，最小方案是什么：保留什么、放弃什么、是否仍满足核心目标；
4. 其他影响决策的事项，包括依赖、重要取舍和待确认问题。
```

说明哪些已有代码依据、哪些仍待验证。约 50% 用于挑战方案的必要性；若无法在保留核心目标的前提下减半，
给出原因和实际可删减的部分。用户采用的范围或行为变化写回同一 Issue。

### 按需求逐项实施

可用下面的短提示启动，具体方法同时由 `engineering_owner` 提示承接：

```text
按照当前 Issue 完成本次开发。
1. 先读 AGENTS.md，按其文档关系读取适用的 SOP.md、TESTING.md、PR_Checklist.md、interact.md；项目存在 capability_contract.json、docs/business_user_guide.md 时，检查本次需求涉及的公开承诺和使用说明。
2. 从 Issue 提取可逐项验收的需求点（Spec Unit，简称 SU），复用已有编号，在任务 todo 中维护 SU -> 代码改动 -> 测试 -> 文档 的对应关系，随着调查更新。
3. 测试策略与测试证据记录方式以 TESTING.md 为准。
4. 在 todo 中说明哪些测试复用、哪些参数化扩展、哪些需要新增；涉及跨模块行为时，指出哪一条具体 scenario 证明组合路径。一条场景可以覆盖多个 SU，不机械地为每个 SU 或 finding 新增独立测试。
```

预计影响的文件是可更新线索；读取授权、写入授权与测试输入各自有明确机械边界：

- 读取：固定来源仓库及本任务受管工作区中的后续修改；未授权私人路径、凭据源与额外仓库不自动开放。
- 写入：在隔离工作区及有效委托内允许受支持的新增、删除、修改、重命名；保护规则作用于实际操作，
  路径越界、链接绕行和重命名两端都须检查。原工作区及其他写责任不能被覆盖。
- 执行：测试使用实际候选、必要依赖和配置；进程、网络与外部副作用依真实授权和执行能力限制。
  测试能看到什么，不由模型之前读过哪些文件决定。

未预测到的相关调用方或文件，在授权范围内应能继续调查和处理。越过真实范围、改变关键目标或
引入未授权外部影响时，保存已完成工作并处理相应决定，不把缺少技术事实推给用户。
普通项目测试随实现更新并接受审核；关键业务验收判据不能由实施者自行放宽。

会话结束或需要压缩时，保留采用版本、候选、修改、证据、未决问题与下一步，再由同一工程责任接续。
已有活跃或未知写入先核清，不以更换会话启动竞争写者。

## 5. 测试、自审与 Draft PR

优先复用项目真实测试和场景，按缺口参数化扩展或补充断言。跨接口、持久化或用户路径的改动，
选择能证明组合行为的验证。临时探针只有覆盖真实且持续的风险时才进入长期测试。
登记脚本不能被实施者改写，不代表它天然由独立作者设计，更不单独证明业务正确。

有效执行证据至少关联受测内容、验证定义、相关环境和完整原件。程序可复用同一有效验证，
但不能从历史里挑一次 PASS 忽略后续尚未核清的失败或未知结果；覆盖缺口、测试定义、环境或候选变化时
判断受影响部分并补验。稳定性复跑、基线试验和新组合试验有各自目的，不一律视为重复。
成功与失败恢复共同使用明确的原执行依据，不固定认定某个旧目录就是当前有效结果。

实施者完成自审、必要文档和真实验证后，在有效委托内创建或更新 Draft PR。
遵循目标仓库提交政策与 PR 模板，仓库外的临时 PR body 不进入提交；正文写实际改动、验证和限制，
引用 Issue 而不再改写一套需求。自审不能代替独立审核，Draft PR 不是成果接受或合并许可。

## 6. 两家公司独立审核 PR，并由原工程负责人处理反馈

两方分别使用 `pr_review_correctness` 与 `pr_review_impact`，均完成针对同一准确候选的完整审查，
共同采用详细审核规范。不同镜头不限制独立发现问题；第二方不能只核第一方的摘要。
首次完整审查均在独立上下文中进行，随后使用共享交流规则交换证据。

- 问题必须有具体触发条件、因果路径、影响和依据；重要主张必要时读调用方、运行已授权验证或复现。
- 原工程负责人修复或反证，审核者对未解决阻断项与修改影响复核，说明已有结论哪些仍适用。
- 未变且仍有效的调查可以复用；新候选必须取得与其内容和范围匹配的两方结论，不机械全仓重读。
- 无问题时可简短交流，不制造争议。事实争议继续补证；产品取舍转有效决定者；关键证据不足保留缺口。
- 普通风格建议不用达成一致。交流有界，超出约定资源或无新证据时说明缺口和下一步，不无限重复。

默认不再追加固定事实核实者、影响核实者和综合者。专项能力仅在存在具体证据缺口时调用，
其结论不能替代双公司正式审核。使用 `PASS`、`REWORK_REQUIRED`、`OWNER_DECISION_REQUIRED`：
仅在本候选所需审核完成、无未解决阻断项和关键证据缺口时 PASS；技术不足不伪装成用户产品决定。
干净路径也需要第二家公司，实际调用投入可能增加；不预先承诺净时间或费用下降。

## 7. 基线前进、集成接收与按委托交付

原目标和委托仍成立时，可以基于 H0 继续形成原工作的候选。界面显示实际基线及是否落后，
长任务在合适时机提前整合。主干移动不自动重做全部调查，但可继续开发不等于可以合并或发布。

使用 `integration_acceptance` 核对准确交付物、有效双公司结论、组合验证、阻断项与交付条件，
默认不触发第三次完整代码审核。既有接收、合并和权限检查必须实际消费这些证据，不能只改名为 PASS。

组合已审且不可变的成员时，复用有效成员结论，补组合验证和独立接收判断；每个成员通过不证明组合通过。
集成修改代码、配置、依赖、启用方式或连接关系，导致受审内容或证据适用性实质变化时，对差异和影响补验、
补充跨公司审核。新的合并 PR 仍满足双审要求，可聚焦组合和新增影响；集成者不能自签独立通过。

合并、启用、部署分别依有效委托进行，并核对实际交付候选。用户已经授权的动作不重复请批，
但测试、审核、接收和用户接受均不自行增加发布权。

## 8. 用户成果验收与交付说明

使用 `user_acceptance` 执行 Issue 阶段已有的用户场景；可运行候选尽早验证，目标环境部分后补。
独立审查检查验收是否充分，不要求每个内部 PR 单独证明整个多 Issue 成果。
当前候选已测、已审、已合并、已启用、用户已接受分别记录，退出码和模型自述不能冒充真实用户接受。

原目标的实现缺口回原工程负责人；目标、范围或关键语义变化回 Issue 与决定；缺执行依据时补相关验证。
使用 `delivery_explanation` 按用户成果说明变化、使用方式、证据和限制。详细机制解释、HTML 或流程图
用于重大变化、理解需要或用户明确要求，不为每个内部 PR 无条件生成。
历史 FSD 完备性关闭检查不恢复为默认关卡。

## 贯穿规则：需求版本、真实进度与恢复

新补充保存为独立修订事实。当前执行继续绑定其原需求、代码和提示；在可证明的结束或受支持接续点，
原工程责任判断澄清、原范围补充或范围变化，并记录实际采用到哪次工作。没有中途安全续接能力时，
先核清原执行，再开始后续执行；停止与撤销走实际停止机制，不排在普通补充之后。

Issue 正文快照、工作版本、执行尝试和代码候选是不同对象。纳入目标不证明已实现，已实现声明不证明通过验证。
旧候选与证据保留原始归属；澄清或缩小范围时可复用仍适用事实，再形成针对新版本的明确结论，不篡改旧 PASS。
不为此另建通用语义失效平台。

项目总览说明目标、当前已确认阶段、正在做的实际动作、等待原因与下一步；必要时显示相关依赖。
目标行为展示来自 Issue，进度来自原执行记录。阶段、活动、结果和用户成果分开；更新时间与信息新鲜度可查，
不虚构百分比、隐藏推理或未接通外部会话的实时状态。页面和秘书读取同一记录，不在每次刷新时重新调用模型。

新版本只默认用于明确新建的工作。在途旧工作按旧流程结束、停止或核清，不自动迁移；
旧准备结果不变成新版写权，未知结果不自动重发，停止不抹除原修改和证据。
流程和提示同时启用，历史按当时采用版本解释，见[版本采用规则](version_adoption.md)。

## 必要产物与按需材料

常用产物为采用的 Issue、必要共享约定、代码候选及实际验证、独立审查意见、交付与成果验收记录。
宿主复用原有工作与执行记录保存精确关系，不要求模型为这些关系另写一套台账。

[FSD](../../prompts/fsd_core_contract.md)、[Bridge](../../prompts/target_state_bridge.md)和
[旧 FSD 关闭提示](../../prompts/issue_closure_fsd_acceptance.md)保留作按需或历史材料，不在 v2 默认源索引中。
是否使用取决于具体证据缺口；它们不能重新成为所有 Issue 的强制前置。

复杂度变化按真实收益复盘：保留必要独立质疑，移除重复转写、交接和无条件重跑。
复盘使用已有工作记录，不为了证明精简效果另建评测平台，也不把未触发当成无价值证明。

## 代码项目核心文档

本仓库中的这些文件是给目标项目继承和项目化的跨语言、跨框架 upstream 基础模板。固定
规范写成完整规则，项目事实 slot 使用 active project-fill marker；目标项目通过最终检查前
必须替换或删除 marker。仅对 sync 工具自身有意义的实现细节放在
`zh/skills/workflow-docs-sync/`，不写入下游模板。

当前模板职责与入口统一见[中文维护入口的目录地图](../../README.md#目录地图)，此处不另维护
一份容易漂移的职责清单。

## Workflow Docs Sync

用户只调用一次 `$workflow-docs-sync`，只提供目标仓库、必选的 `zh` / `en`，以及成功后是否
创建 draft PR。Skill 内部解析 canonical upstream checkout；无法定位时使用仓库外临时 shallow clone，
并在整轮固定目标 HEAD 与上游 SHA。

- 写文档前至少以 `git ls-files -z` 建立范围；事实与政策的核验方法遵循
  [canonical Skill](../../skills/workflow-docs-sync/SKILL.md)，不在本说明重复定义。
- Architecture、Capability / User Behavior、Testing、Governance 是覆盖维度，不是固定 Agent
  拓扑。主 Agent 可独立完成，也可按模块、调用链、风险或证据类型动态委派只读调查。
- 主 Agent 是目标工作区唯一写入者。全量质疑九份文档后只改错误、缺失或失真部分；正确
  内容保持零 diff，不输出 disposition ledger、run state 或 receipt。
- 测试环境由真实命令、副作用、CI 能力和项目政策决定；记录实际环境、隔离、残留和清理，
  不把一种环境实现固化成跨项目规则。
- 复核优先使用 fresh-context、blind-first independent reviewer；不可用时明确标记
  self-review，不能冒充独立复核。BLOCKER 与无需产品决策的 actionable WARN 修复后复核。
- `sync_docs.py prepare` 先验证固定 object 与 language 下九份 UTF-8 source template 及非 PR
  active-marker invariant，再补齐缺失模板；`check` 重读同一 pinned source，并只读验证最终
  HEAD、dirty 范围、editable path 无 index/worktree 分叉、九份普通 UTF-8 非空文件、JSON
  object、active marker，以及存在时为 UTF-8 的 `.gitignore`。最终 bytes 的 whitespace 使用
  临时非 Git 目录和固定 Git 规则，不继承目标仓库 attributes。Checker 不解析 Markdown，也不
  验证目标项目 capability、测试层级或文案质量。单一 final-bytes 路径依赖同步范围外 dirty
  path 始终被拒绝；若未来放宽 allowlist，必须重新评估 whitespace 覆盖。index/worktree 分叉
  拒绝按 path 聚合两侧 status，并覆盖 index 删除或 rename source 后同路径 untracked / ignored
  重建；它消除的是两个发布候选，不是第二套 whitespace 检查。
- 安装器在任何删除或复制前验证 source/目标祖先、source symlink、Claude frontmatter 的标准
  分隔和会被复制的 ignored source residue；只精确清理废弃 reviewer Skill，不保存安装状态或
  来源 receipt。
- PR body 临时 Markdown 始终位于仓库外。commit、push 和 draft PR 创建只在用户要求且检查
  成功后，由通用 GitHub 发布能力完成。
- 最终机械检查只证明最终仓库状态，不证明调查、测试或复核执行历史。

## 上游双语语义等价审核 SOP

本 SOP 只适用于维护 `wlvh/coding-workflow` 上游仓库，不写入下游项目继承的
`AGENTS.md`、`architecture.md`、`TESTING.md`、`PR_Checklist.md` 或 `SOP.md` 模板。
目标是定期确认中文锚点文档的语义变化已经被英文派生路径吸收，或已经显式记录
`en-pending` follow-up。

触发节奏：每月最后一个工作日执行一次；如果本月修改过任意中文锚点核心文档、
`zh/README.md` 或 `zh/skills/workflow-docs-sync/`，则必须在下一次主线 PR 合并前执行。

### Step 1：确认审核范围

- 做什么：列出本轮要审核的中英配对文件，只覆盖本仓库声明的双语入口、模板和 sync 工具文档。
- 去哪看：`zh/README.md` 的“目录地图”、`sync_docs.py` 的 `CORE_FILES` 和中英模板目录。
- 做完如何验收：每一项必须是 `zh/路径 -> en/同名路径`；Skill 实现只在 canonical
  `zh/skills/workflow-docs-sync/` 维护，不创建英文实现副本，也不得出现 `.en.md`、
  `.en.json`、`.en.sh` 文件路径。

### Step 2：收集中英文变更证据

- 做什么：对每个配对文件查看自上次审核点以来的中文 diff 和英文 diff；没有明确上次审核点时，使用用户指定 base，或使用当前 PR base。
- 去哪看：`git log <base>..HEAD -- <path>`、`git diff <base>..HEAD -- <path>`、PR body 的“文档影响 / Review / 修复记录”。
- 做完如何验收：每个配对文件都有状态：`stable`、`zh_only`、`en_only`、`both`；`zh_only` 和 `en_only` 必须进入人工判断。

### Step 3：逐项判断语义等价

- 做什么：以中文 diff 为锚，判断英文是否覆盖同一流程、能力边界、验收不变量、路径和拒绝 / 追问规则；`both` 状态重点判断英文是否是中文语义派生，而不是独立创作。
- 去哪看：中文文件当前内容、英文文件当前内容、`zh/README.md` 的中文锚点规则和
  `zh/skills/workflow-docs-sync/SKILL.md` 的领域语义。
- 做完如何验收：每个配对文件得到一个结论：`ok`、`missing translation`、`stale en`、`contradiction`、`intentionally pending`；除 `ok` 外都必须记录具体文件、段落和建议处理方式。

### Step 4：生成审核结论

- 做什么：把本轮审核结果写成可转交的 issue、PR comment 或本地审查记录。
- 去哪看：本节 SOP、Step 2 的 git 证据、Step 3 的逐项判断。
- 做完如何验收：结论至少包含审核 base / HEAD、审核日期 UTC、配对文件清单、每项状态、需要修复的英文段落、是否存在 `en-pending`、下一步 owner。

### Step 5：闭合处理

- 做什么：对 `missing translation`、`stale en`、`contradiction` 生成修复任务；对暂不修的项确认 PR body 或 issue 中有 `en-pending` 和 follow-up 边界。
- 去哪看：本轮审核结论、相关 PR body 或 issue。
- 做完如何验收：所有非 `ok` 项都有明确 follow-up；如果本轮完成修复，重新执行 Step 2 和 Step 3，直到结论为 `ok` 或 `intentionally pending`。

反向规则：任何对 `AGENTS.md`、`TESTING.md`、`PR_Checklist.md`、`SOP.md`、
`architecture.md`、`interact.md`、`capability_contract.json` 或
`docs/business_user_guide.md` 的修改，如果只对本仓库 sync 工具特殊场景有用、对下游
继承项目无意义，必须迁移到 `zh/README.md`、`zh/docs/development_workflow/` 或
`zh/skills/workflow-docs-sync/` 后再合入。

配套边界：`en-pending` 只属于维护 `wlvh/coding-workflow` 上游仓库时的双语治理语境，
不得作为通用目标仓库审计 BLOCKER，避免中文或英文单一路径项目被误拦截。
