# 固定版本采用与用户发起更新

本文件规定 Tongxu 等编程执行系统怎样采用 [coding-loop v2](README.md)。
本仓库提供规范、提示和源索引；具体导入、权限、执行、界面与兼容逻辑由下游实现。
读到本文件或导入成功不表示下游已经支持新流程。

## 1. 来源与职责

编程模型的职责、方法、审查、交流、修复、接收和验收等自然语言行为模板，以 coding-workflow
为唯一维护来源。范围包括 system、developer、任务输入中的行为段，不以文件扩展名区分。
本地角色文件、代码硬编码字符串和自由追加 taskPolicy 都不能形成另一套工程政策。
需要新的行为规则时，修改上游，再通过本流程采用。

Tongxu 提供当前 Issue、用户原话、项目 AGENTS.md、候选、证据等实际输入，执行工具、工作区隔离、
权限、停止、费用与结果格式检查。这些事实不能授予不存在的权限；模型提示也不能代替机械限制。
若需要面向模型的公共运行说明模板，模板同样由上游编程提示维护，宿主填入真实能力和参数。
非编程秘书、项目管理、账号与安装提示不在本轮迁移范围。

README 是人的流程入口；[coding_workflow.json](../../prompts/coding_workflow.json)列出按用途加载的
准确源文件。角色文件和共享片段在上游维护，不在下游通过模型总结、截短或改写后冒充原文。
共享片段并不要求一个新模型调用；同一工程负责人可以在不同阶段使用相应用途。

## 2. 最小源索引

v1 索引使用以下字段，路径全部相对 coding-workflow 仓库根：

| 字段 | 含义 |
|---|---|
| schemaVersion | 索引格式版本，当前为 1 |
| workflowId / workflowVersion | 编程规范身份与版本，当前为 coding-loop / 2 |
| executionContract | 下游必须明确支持的执行约定，当前为 coding-loop-v2 |
| language | 源语言；当前可直接采用的编程提示为 zh |
| entrypoint | 同一提交内的人类流程入口 |
| roles | 用途到有序 promptPaths 的映射；每个 promptPaths 都包含公共规则 |

索引不描述任意节点、循环、路由或插件，也不执行文件中的命令。下游对这个明确的协议版本实现控制流，
不把 README 当通用编排语言。当前用途及其文件以索引为准；英文提示翻译状态见
[English prompt status](../../../en/prompts/README.md)，未完成翻译不冒称英文可执行提示包。

使用 Git 提交确定所有源内容，无需在源索引自身维护一套会递归变化的内容摘要。
下游导入时再生成实际采用记录中的文件摘要与完整包摘要。

## 3. 一次更新怎样完成

1. 区分用户的“检查更新”和“升级并启用”。前者只比较，后者在既有委托内完成准备、适配、
   验证与启用，不重复增加中间批准。实质产品选择或超出委托的动作才处理对应决定。
2. 将请求时选定的 main、tag 或指定版本解析为一个完整 Git commit。README、索引、prompt 和引用的
   编程政策均从该提交读取。本轮上游继续移动不改变已选目标，不混用两次下载的不同版本。
3. 对比当前采用内容，说明哪些变化是解释、提示或控制流程变化。没有对应控制能力时保持“待适配”，
   用正常工程任务完成所需代码改动；不能靠把新版 README 放入提示来假装已经支持新流程。
4. 保存完整源快照，准备与其配套的执行流程，完成针对真实变化的验证。需要独立审核的改造遵循
   实际采用的审核规则与用户明确要求。文件哈希正确不证明语义或运行能力正确。
5. 只有完整包和相应控制流程都可用，才一次性切换新工作的默认版本。导入、适配或验证失败时，
   现行默认版本保持完整，不把部分新文件与旧流程一起启用。

更新作业自身继续绑定开始时的流程；对候选新版本的试运行单独记录，不中途更换用于判断本次升级的规则。
上游只需源索引，下游只需明确导入/检查与固定采用记录；不要求导出服务、插件平台或通用迁移引擎。
本仓库现有 workflow-docs-sync 只同步其声明的项目文档，不承担这项运行流程升级。

## 4. 实际采用记录

复用下游已有的工作、执行与原件存储；至少能关联：

- 上游仓库、完整 commit、索引原文及摘要；
- 每个实际源路径、原文字节及摘要，有序提示组合及完整包摘要；
- 下游执行流程/接口版本、实际模型供应商与模型、相关工具与能力版本；
- 本次需求快照、工作/执行身份、候选与授权引用；
- 动态参数和最终实际发送的输入，保证源模板与实际执行可核对。

源文件清单和运行加载应使用同一个采用记录，避免 manifest 与代码常量维护两份不同来源。
用户界面提供可读版本、来源链接、适用的新工作范围与待解决条件，不要求用户手写 JSON 或 SHA。
固定的是工作流来源与单次执行依据，不要求把原生工具的具体版本、路径或二进制摘要变成长期准入白名单；
运行兼容性按下游有效的最低要求与实际能力检查处理。
运行可以离线使用已验证的快照；缺文件、未知协议、被修改的快照或不支持的执行能力明确失败，
不联网追 main，也不使用本地临时提示或同公司模型静默顶替。

## 5. 新旧工作与历史

- 在明确的工作登记边界固定流程和提示身份，在首次模型发送前核对。准备与首次发送之间默认版本
  改变，不能改变已登记工作的实际规则。
- 默认只给新建工作采用新版。在途旧工作按原版本完成、停止或核清，不把新提示注入原执行。
- 已准备但未实施的旧工作不继承新版工具、范围或写权。要改用新版，明确建立下一工作版本或重新准备，
  核清原责任并沿用真正有效的委托；不能改贴状态。
- 需求修订与流程升级分别记录。新要求被采用不自动升级旧工作的流程；授权内的需求修订仍需明确记录
  采用版本和候选关系，旧事实可复用，旧通过结论不直接转贴。
- 旧结果按其当时已采用的源快照和规则校验，不能用当前全局版本否定或重新解释历史。
  只核对调用者自报摘要不足以证明采用来源，须联系原已登记源与完整记录。
- 活跃或结果未知的原执行先核清，不通过切换版本重复发送。停止保留原结果与修改。
- 回退只改变后续新工作的默认选择；已经发出的新版执行仍按其原身份处理。
  旧写入路径在没有在途责任后退役，保留必要历史读回，不永久维护两个完整引擎。

## 6. 下游最小验收

验收覆盖实际采用与执行，不只检查文件是否存在：

1. 更新过程上游 main 再次移动时，本次仍完整使用已固定的同一提交。
2. 编程模型实际收到的行为段可追到该提交的模板；本地自由政策、残留硬编码或被摘要替换的源不能绕过检查。
3. 缺文件、摘要变化、未知协议或缺执行能力时，升级保持未启用，现行版本仍完整可用。
4. 两家公司实际完成同一 Issue/候选的独立审查并交流；少一家公司不能以角色名或提示文本充数。
5. 正常入口完成持续调查实施，补读预测之外的材料、受控新增文件，并让真实测试包含该候选和必要输入。
6. 安装新版本后，旧 prepared、活跃、失败、停止、未知和已完成工作仍保持原含义；历史能够读回，
   未知不重发，旧准备不扩权。新工作、旧工作和一次需求修订可以同时辨认。
7. 集成候选取得对应验证与独立结论，接收默认复用有效双审，不增加第三次完整代码审核。

这些是下游实现的完成条件。本仓库发布本规范，不表示上述运行验收已经通过。
